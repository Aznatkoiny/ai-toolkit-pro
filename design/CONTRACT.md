## 0. Intent summary

The plugin equips AI scientists' coding agents with deep-learning model-building judgement from Deep Learning with Python 2E: given a problem description (data modality, task type, dataset size), it routes to the architecture family, loss/activation pairing, evaluation protocol, and workflow the book's decision rules select — helping scientists decide what makes sense for their problem rather than defaulting to the fanciest model. Deliverables are a structured `MODEL_PLAN.md` (with the governing rule cited) and a runnable `starter_model.py` Keras scaffold, both written into the scientist's project workspace. Per INTENT: runtimes are all three (local interactive, CI/headless `-p`, cloud routines); the shipped plugin is fully self-contained (book content distilled at build time into bundled references — zero runtime external systems); side effects are workspace file writes only; suite tolerance ~24 tasks with `--max-cost-usd 25`. Design decision resolving INTENT open question 1: starter code is emitted in Keras 3-compatible idiom (`import keras`) with a compatibility note; bundled patterns are modernized from the notebooks' TF/Keras 2.x code, and this modernization is a maintainer-owned rot surface.

### CAP-2 — Emit the exact loss/activation pairing

**Capability:** `MODEL_PLAN.md` states last-layer activation + loss (+ headline metric) exactly matching the book's ch6 table for the stated task type: binary→sigmoid+binary_crossentropy; multiclass single-label→softmax+categorical_crossentropy (or sparse variant); multilabel→sigmoid+binary_crossentropy; scalar regression→no activation+mse.

**Chosen composition:** same `advise` skill. The pairing table appears verbatim in the SKILL.md body (first 5k tokens) AND as machine-readable `data/pairings.json` inside the skill directory; a **skill-lifecycle hook** (SKILL.md frontmatter `hooks:`, active only while the skill runs) — PostToolUse, matcher `Write|Edit`, exec-form command `${CLAUDE_PLUGIN_ROOT}/skills/advise/scripts/lint_outputs.py` (plugin-root substitution is the documented hook-path form; no `${CLAUDE_SKILL_DIR}` reliance) — validates any write to `MODEL_PLAN.md` (required sections present; task-type ↔ activation+loss consistency against pairings.json) and any write to `starter_model.py` (CAP-4 checks), exiting 2 with a stderr correction message on violation.

- **C2 — Context economics:** pairing table ≈ 300 tokens inside the body budget already counted in CAP-1; `pairings.json` is hook-input only, never loaded into context. Hook adds zero always-on cost outside skill runs (lifecycle-scoped — not plugin hooks.json).

PreToolUse full-content gating was considered and rejected (see §3): Edit payloads carry only old/new fragments, so pre-validation of a whole document is unreliable.
