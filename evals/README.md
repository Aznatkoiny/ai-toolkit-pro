# Evaluation suite

This directory is this plugin's frozen evaluation suite, generated by
`/plugin-forge:build-evals`. It is self-contained: the suite runs without
plugin-forge installed, so it outlives its builder. "Done" for this plugin
is defined by this suite going green — not by files existing.

## Layout

```
evals/
├── README.md               # this file
├── registry.yaml           # alias -> versioned suite id (score continuity)
├── bin/run.py              # vendored stdlib-only runner (copied in by build-evals)
├── settings/
│   └── harness-settings.json  # sandbox + scoped allowlist (copied in by build-evals)
├── targets/
│   ├── default.yaml        # plugin loaded, pinned model, sandboxed
│   ├── no-plugin.yaml      # RED baseline: bare Claude, must fail capability
│   └── crowded.yaml        # + distractor plugins, for trigger measurement
├── suites/
│   ├── capability.yaml     # the hill to climb (low pass expected pre-build)
│   ├── regression.yaml     # graduated + mined tasks, must stay ~100%
│   └── triggers.yaml       # trigger precision/recall under listing pressure
├── tasks/
│   └── _example/           # complete runnable example — copy per task
│       ├── task.yaml       # id, graders, scoring, timeout (the contract)
│       ├── instruction.md  # the prompt: end state + proof + invariants + bound
│       ├── fixtures/       # files copied into the fresh workspace pre-run
│       └── reference/      # reference solution — staged OUTSIDE the workspace
├── judges/
│   ├── fact.yaml           # factual-consistency judge (A–E + Unknown)
│   ├── rubric.yaml         # one-dimension Y/N/Unknown judge
│   └── battle.yaml         # pairwise old-vs-new judge (win-rate proof)
├── labels/
│   └── labels.jsonl        # human golden labels for judge calibration
└── distractors/            # small plugins loaded by the crowded target
                            # (referenced as ../distractors/<name> from targets/)
```

A sibling `evals-holdout/` directory (same shapes, never copied into build
worktrees) holds the holdout tranche — see below.

## Running the suite

Standalone, from the plugin root:

```bash
python3 evals/bin/run.py run --suite capability --plugin-dir . --evals-dir evals
python3 evals/bin/run.py run --suite capability --plugin-dir . --evals-dir evals --target no-plugin  # RED baseline
python3 evals/bin/run.py run --suite triggers --plugin-dir . --evals-dir evals      # crowded by default
python3 evals/bin/run.py reference --suite capability --plugin-dir . --evals-dir evals  # grade the references
```

`bin/run.py` is a vendored, single-file, stdlib-only copy of the plugin-forge
harness core, copied in at generation time by `/plugin-forge:build-evals`.
If plugin-forge is installed, `forge-eval` offers the same subcommands
(`run | red | reference | smoke | metaeval | graduate | doctor`) plus
`--trials`, `--jobs`, `--task`, `--max-cost-usd`, `--dry-run`, and delegates
to the vendored runner when present.

Every run writes `runs/<ts>/` (events.jsonl, summary.json, transcripts/,
report.html) and prints, as its FINAL stdout line, the machine-readable
scoreboard:

```
FORGE_EVAL: suite=<name> version=v<N> passed=<X>/<Y> pass^<k>=<0.00> cost_usd=<C> RESULT=PASS|FAIL
```

Exit code is 0 iff `RESULT=PASS`. CI and goal-loop evaluators key off this
line alone. Timeouts are recorded as `timeout` (exit 143); trials hit by
`api_retry` events are recorded `unverified` and excluded from pass rates.

## Registry and versioning

`registry.yaml` maps stable aliases to versioned ids (`capability` ->
`capability.dev.v1`, OpenAI-registry style). Scores are only comparable
within one versioned id; any edit to a frozen suite bumps the version
(`/plugin-forge:arm-evals` does this and re-freezes). Never edit a
versioned id's files in place after recording runs against it.

## Targets

A target is a named `claude -p` launch config (model, permission mode,
allowed tools, plugin source, settings). Three ship by default:

- **default** — the plugin under test, sandboxed, pinned model.
- **no-plugin** — the RED baseline. It declares `plugin: false` explicitly,
  so the harness launches bare Claude even when `--plugin-dir` is passed.
  Every capability task must fail here before the suite is armed; a task
  that passes without the plugin has no signal and gets hardened or cut.
- **crowded** — the plugin plus a distractor plugin set, loaded via
  repeated `--plugin-dir`. Trigger precision/recall measured in a bare
  session is optimistic; this target measures it under the real ~1%
  listing budget competition.

Add a new target file to A/B a model or plugin version against an
unchanged suite.

## Suites

- **capability** — end-to-end tasks; expect low pass rates until the
  plugin is built. Headline metric is `pass^k` (all k trials pass), the
  reliability bar for business/scientific use.
- **regression** — must stay ~100%. Fed by `graduate` (tasks passing >90%
  move here) and by `/plugin-forge:build-evals mine` (captured trace
  failures become tasks).
- **triggers** — paraphrase batteries with `should` / `should_not` prompt
  sets, scored as activation precision/recall against the crowded target.
  Positive AND negative cases are mandatory.

## Tasks

Each task is a directory under `tasks/` with `task.yaml` (schema documented
inline in `tasks/_example/task.yaml`), `instruction.md` (end state + proof
command + invariants + turn bound), `fixtures/` (staged into a fresh
isolated workspace per trial), and `reference/` (staged OUTSIDE the
agent-visible workspace; `reference` runs must pass their own graders
before the suite arms).

Grader doctrine, in priority order: workspace checks (file_exists,
file_contains, json_match, git_diff, exit_code, numeric — numeric REQUIRES
`tolerance`), transcript checks (loose tool usage, turn/token budgets —
never tool order), state_check commands, judges (one dimension per call),
trigger batteries. Deterministic before model-graded, always.

## Judges and calibration

Judge specs in `judges/` follow the OpenAI modelgraded-spec shape: a
`prompt` with `{input}` / `{completion}` / `{criteria}` placeholders,
`choice_strings` (Unknown is always a legal choice), `choice_scores`,
`eval_type: cot_classify`, and a pinned cheap `model` that is never the
target model. The runner renders the prompt into an isolated
`claude -p --bare` call with a JSON schema returning
`{choice, rationale, evidence}` so failures can be triaged against the
agent transcript side by side.

Judges must be calibrated before the suite freezes: run
`python3 evals/bin/run.py metaeval --plugin-dir . --evals-dir evals` (or
`forge-eval metaeval`) to score each
judge against the human labels in `labels/labels.jsonl`; agreement must be
>= 0.85. Ten to twenty labels per judge is the working minimum.

### labels.jsonl format

JSONL holds no comments, so the format is documented here. One JSON object
per line, fields:

| Field | Required | Meaning |
|-------|----------|---------|
| `judge` | yes | judge spec name (`fact`, `rubric`, `battle`) |
| `judge_prompt_version` | yes | version of the judge prompt this label calibrates (agreement baselines are stored per version) |
| `task_id` | yes | task the sample came from |
| `trial` | no | trial number, when the sample came from a real run |
| `input` | yes | the task input shown to the judge (`{input}`) |
| `completion` | yes | the completion the judge graded (`{completion}`) |
| `criteria` | yes for fact/rubric | the criterion text (`{criteria}`) |
| `completion_baseline` | yes for battle | the baseline completion |
| `choice` | yes | the HUMAN-assigned choice from the judge's `choice_strings` |
| `labeler` | yes | who labeled it (`human` or a name; never a model) |
| `labeled_at` | yes | ISO date |
| `notes` | no | why the label is what it is |

The two records shipped in `labels/labels.jsonl` are worked examples (one Y,
one N for the rubric judge); replace them with labels drawn from real
transcripts of YOUR tasks.

## Holdout tranche

A tranche of tasks lives in `evals-holdout/` (sibling of `evals/`, same
layout). It is excluded from the build worktree, so the building agent
never sees those graders and cannot overfit to them. Verification runs
visible + holdout; the honest claim after green is "green + holdout +
triage", never "correct".

## Permission story

`settings/harness-settings.json` is how eval runs stay autonomous WITHOUT
`--dangerously-skip-permissions`: OS-level sandbox enabled (fail if
unavailable, no unsandboxed escape hatch), an empty strict network
allowlist (evals are hermetic — mock fixtures, no live endpoints; widen
`allowedDomains` only to endpoints the plugin's contract declares),
credential env vars masked or denied, and `permissions.allow` scoped to
exactly the file tools and sandboxed Bash the tasks need, with WebFetch,
WebSearch, git push, and secret files denied outright.

## The living suite

This plugin ships a `trace-capture` PostToolUse hook that appends brief
tool traces to `${CLAUDE_PLUGIN_DATA}/traces/*.jsonl` (size-capped, always
non-blocking). When real usage fails, `/plugin-forge:build-evals mine`
turns those traces into new regression tasks; saturated capability tasks
graduate; and `judges/battle.yaml` proves each iteration beat the last by
win rate on identical tasks.
